Getting started

To illustrate how to use ParallelMCMC, this guide will sample from a two-dimensional banana-shaped density with parallel MALA.

Our goal is to sample from the following distribution:

\[\log p(x) = -\frac{1}{2}\left(\frac{x_1^2}{100} + \left(x_2 + 0.1\, x_1^2 - 1\right)^2\right).\]

Its Hessian changes with $x$, so it tests the Hessian-vector products in a way that a Gaussian target would not, as a Gaussian's Hessian is constant in $x$.

Installation

Before we can sample, we need to install the necessary packages. We of course will need ParallelMCMC, but Parallel MALA also needs Hessian-vector products of the log-density. You can write these yourself, but often it is more convenient to get them from an automatic differentiation (AD) backend. ParallelMCMC does not depend on any AD package, so you must load the one you want; this guide uses ForwardDiff.

pkg> add ParallelMCMC ADTypes ForwardDiff FlexiChains AbstractMCMC

ADTypes provides AutoForwardDiff(), FlexiChains provides ess and rhat, and AbstractMCMC provides MCMCThreads().

using ParallelMCMC
using ADTypes, FlexiChains, ForwardDiff, Random
using AbstractMCMC: MCMCThreads

Define the target

A DensityModel needs a log-density, a gradient, and the number of unconstrained parameters. The log-density may omit its normalizing constant.

function banana_logdensity(x)
    a = x[2] + 0.1 * x[1]^2 - 1
    return -(x[1]^2 / 100 + a^2) / 2
end

function banana_gradient(x)
    a = x[2] + 0.1 * x[1]^2 - 1
    return [-x[1] / 100 - 0.2 * x[1] * a, -a]
end

model = DensityModel(banana_logdensity, banana_gradient, 2; param_names=[:x1, :x2])

The gradient here is written by hand, but it does not have to be. Defining models shows how to get it from an AD backend instead.

Tune the step size

MALA is sensitive to its step size, so it is important we use one that is properly tuned to our problem. If the step size is too large, most proposals are rejected; if it is too small, the chain moves slowly and successive samples are highly correlated. AdaptiveMALASampler tunes the step size during warmup, so we run it first and reuse the result.

tuning = sample(
    MersenneTwister(42),
    model,
    AdaptiveMALASampler(0.1; n_warmup=500),
    750;
    initial_params=zeros(2),
    discard_warmup=true,
)

epsilon = last(vec(tuning[:step_size]))
0.6857427080770881

The 750 transitions include the 500 warmup transitions, and discard_warmup=true removes those from the returned chain. After warmup the step size is fixed, so we take the last value of :step_size, which the chain stores next to the parameters.

Check the tuned step size

A tuned step size that collapses toward zero usually means that the gradient is wrong or that the parameters have very different scales. Adaptation cannot fix either problem.

Run parallel MALA

We can now pass the tuned step size to ParallelMALASampler. The model has no hand-written Hessian-vector product, so backend=AutoForwardDiff() tells the sampler to compute one by differentiating banana_gradient.

sampler = ParallelMALASampler(epsilon; T=64, backend=AutoForwardDiff())
chain = sample(MersenneTwister(43), model, sampler, 2_000; initial_params=zeros(2))

Choose T and the DEER controls

Of the DEER settings, T matters most for speed. Each DEER iteration updates all T states of a block at once, and the solve usually needs far fewer iterations than T. In our tests on a logistic regression with 25 parameters, a block of 64 transitions took 12 to 16 iterations, while a block of 4096 took 23 to 31. Zoltowski et al. (2025) saw the same thing on a GPU, where whole chains of up to 64,000 MALA transitions converged in tens of iterations.

This means a longer block needs far fewer sequential steps per sample, and on a GPU the default T=64 leaves most of that unused. The limits are memory and the size of the GPU: once evaluating the model at T states takes noticeably longer than at one state, a longer block stops paying off. A CPU has much less room for parallel work, so there a long block mostly adds work.

A simple way to choose T is to get the model sampling correctly with the default, then double T and time sample until it stops getting faster. In exact arithmetic the solve finishes within T iterations, so maxiter only comes into play once T is larger than it.

The other keywords control the solve:

  • jacobian=:stoch_diag, the default, estimates the diagonal of each transition's Jacobian with probes random vectors. Each extra probe makes the estimate less noisy and costs one more Jacobian-vector product per transition.
  • jacobian=:diag computes the diagonal exactly with one Jacobian-vector product per parameter. Use it to check results on small models.
  • jacobian_damping and jacobian_clip scale and clip the Jacobian diagonal before each scan. The defaults suit most targets; for multimodal targets, try jacobian_damping=0.5. See Damping and clipping the Jacobian.
  • maxiter, tol_abs, and tol_rel decide when the solve stops. See ParallelMALASampler for the exact rule.

If a block reaches maxiter before it meets the tolerances, the sampler still returns its states as samples and logs one warning for the run. Troubleshooting explains what to try.

Use the returned chain

sample returns a FlexiChains chain. Index it with the parameter names from the model, as in chain[:x1], and use chain[:logp] to get the log-density of each sample.

Run several chains

To check convergence, run several chains and compare them with $\hat{R}$.

Multiple chains are experimental

Parallel MALA and multiple chains both get their speed from the same hardware. DEER does more total work than sequential MALA and only wins when that work runs in parallel on hardware that would otherwise sit idle. With many chains the hardware is already busy, so the extra work is no longer free, and plain sequential chains can end up faster. Zoltowski et al. (2025) observed this on a GPU: with 32 chains, sequential MALA was slightly faster than parallel MALA. How best to split resources between more chains and longer chains is still an open question. Run a few chains to compute diagnostics such as $\hat{R}$, not to sample faster.

Start Julia with several threads, for example julia -t 4, so that MCMCThreads() can run the chains at the same time:

chains = sample(
    model,
    sampler,
    MCMCThreads(),
    2_000,
    4;
    initial_params=fill(zeros(2), 4),
)
